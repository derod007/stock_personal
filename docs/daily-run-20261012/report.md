## 1. 업종 수집

운영 스캐너는 `data/raw/cache/sector/sector_<코드>.json`만 씁니다. `data/cache/sector`는 이번 경로가 아닙니다.

예약 실행은 `--cache` 없이 돌아 `SectorMap::resolve(..., useCache=false)`입니다. 캐시를 읽어 업종을 정하지 않고 네이버를 다시 조회한 뒤, 유효한 업종만 캐시에 씁니다. 자리표시자 `기타`는 일반 주식 캐시를 덮어쓰지 않습니다(PR #67).

당시 스캔 JSON(실행 창 안 mtime) 기준 100종목:

| 구분 | 건수 |
|---|---:|
| 유효 업종명 | 99 |
| 자리표시자 `기타` | 1 (`200000.KS`) |
| 파일 없음 | 0 |
| 읽기 오류 | 0 |
| 업종명은 있는데 bucket=`other` | 2 (수집 실패로 세지 않음) |
| 이번 실행 중 캐시 기록 | 99 |
| 이번 실행보다 오래된 캐시 | 1 (`200000.KS`, 2026-09-09, 내용도 `기타`) |

`000150.KS` 두산, `028260.KS` 삼성물산은 업종명이 `복합기업`입니다. bucket/`sector_label`이 `기타`인 것은 분류 버킷이고, 자리표시자 업종명 `기타`가 아닙니다.

PR #67 이후: 99종목은 이번 실행에서 실제 업종명으로 캐시가 갱신됐습니다. `200000.KS`는 당시 조회도 `기타`였고 기존 캐시도 `기타`라, “자리표시자가 실제 업종으로 바뀌었는가”의 사례가 아닙니다. Yahoo 심볼이 404라 분석 자체를 못 한 종목입니다. 네이버가 업종 코드를 안 주는지, 매핑 실패인지는 이번 자료만으로 단정하지 않습니다.

현재 캐시만으로 당시 수집을 확정하지 않았습니다. 당시 근거는 스캔 JSON입니다. 현재 캐시 mtime이 실행 창 안인 99건은 이 실행이 쓴 결과와 일치합니다.
